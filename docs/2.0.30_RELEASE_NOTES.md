# Website Core 2.0.30

Release candidate: 2026-10-25

## Split-runtime recovery repair

- Resolves backup configuration from `WC_CONFIG` and upload/media locations
  from the installed paths instead of assuming all mutable data lives beneath
  the public document root.
- Restores each protected file to that same configured runtime root.
- Preflights every changed destination before importing the database. A
  panel-owned file that truly needs replacement now stops safely before SQL is
  changed.
- Skips byte-identical destination files, allowing immutable `.htaccess`,
  module, and theme files to remain untouched on split-ownership hosts.
- Adds an owner-only Download action for verified recovery points. Archives are
  streamed from protected storage with private/no-store and nosniff headers and
  the download is recorded in Audit.

## Live finding

The hosted 2.0.29 build successfully created and verified a 1.63 MB MariaDB
recovery point containing 41 tables and 57 protected files. Its restore safety
snapshot also succeeded, but file restoration then stopped at the public
`config/.htaccess`, which had been written by the hosting panel and was not
writable by PHP. System Health remained clean after the stopped restore.

The underlying problem was broader than one file: the installation uses a
private runtime outside the document root, while the backup service still
assumed public `config/` and `upload/` paths. Version 2.0.30 aligns recovery
with the same runtime-path contract used by the installer.

## Verification required

Automated PHP 8.4/8.5, MySQL, MariaDB, installer, package, and artifact gates
must pass before deployment. After upload, create a fresh 2.0.30 recovery
point and verify its download and restore before update rollback, module
disable/uninstall/purge, or broken-module quarantine tests continue.

No database migration or module API change is required.
