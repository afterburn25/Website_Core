# Website Core 2.1.0

Core 2.1.0 introduces dormant, module-activated commerce and public customer
accounts. The implementation is universal, but no store or account surface is
visible merely because Core contains the code. An enabled industry module must
declare each feature it supports.

## Module-owned availability

Modules opt into `commerce.catalog`, `commerce.cart`, `commerce.checkout`,
`commerce.orders`, and/or `accounts.customers` through the supported
`ModuleContext` API. Core derives routes, administrator navigation,
permissions, search results, dashboard summaries, and public entry points from
those declarations.

- No declaration: no visible option and public routes return a branded 404.
- Disable or uninstall: UI disappears and data is preserved.
- Re-enable or reinstall: existing products, orders, and accounts return.
- Explicit data purge: package-owned rows in both module and Core feature
  tables are removed in dependency-safe order.

The Catering reference module 0.2.0 enables all commerce surfaces, pickup and
delivery fulfillment, and customer accounts. It supplies Store and My Account
navigation defaults for new installations.

## Products, cart, and inventory

Administrators can create products with a stable SKU, URL slug, description,
price, image URL, sort order, featured state, availability, and optional stock
tracking. The public storefront reads current prices and availability. Cart
quantities are bounded and revalidated before checkout.

Order placement uses a database transaction. Tracked stock is decremented
atomically; a concurrent checkout that loses the final stock cannot create an
oversold order. Cancelling an order restores tracked inventory exactly once,
and cancelled orders cannot be reopened accidentally.

## Checkout and manual payments

The built-in no-gateway methods are:

- Venmo
- PayPal
- Cash App

Each method has an administrator on/off switch and customer-facing payment
instructions. Cash is intentionally not included. Core never marks these
orders paid automatically: new orders begin with payment status `pending`, and
staff records `paid`, `refunded`, or `void` after verifying the external
transaction.

Checkout supports module-declared pickup, delivery, and shipping choices,
validates required addresses, rate-limits submissions, queues customer and
owner notices, creates immutable item snapshots, and emits the signed-webhook
event `commerce.order.placed` after the transaction commits.

## Customer accounts

Public customer accounts are distinct from protected administrator accounts.
The optional account surface includes:

- module-scoped email identity and strong password storage;
- registration, sign-in, sign-out, and rate limiting;
- 30-minute one-time password recovery links through Core transactional mail;
- editable name and phone profile, with email kept identity-stable;
- orders placed while signed into that account shown in order history; and
- an administrator customer list with disable/restore controls and auditing.

A disabled customer is rejected on the next request. Account routes and the
Customers admin category do not exist functionally when the active module has
not declared `accounts.customers`.

## Administration integration

The polished Store and Customers workspaces use the shared Core shell,
permissions, responsive layouts, CSRF protection, validation, audit history,
global search, dashboard order snapshot, and no-rewrite/subfolder URL format.
The role editor lists optional permissions only while the matching feature is
active.

## Upgrade

Migration `2026_10_25_0029` creates five additive tables:

- `commerce_products`
- `commerce_orders`
- `commerce_order_items`
- `customer_accounts`
- `customer_password_resets`

Existing sites migrate on the first request after uploading the full 2.1.0
payload. Existing module/content data is untouched. Administrators should then
open Store settings and enable at least one manual payment method before
publishing the store.
