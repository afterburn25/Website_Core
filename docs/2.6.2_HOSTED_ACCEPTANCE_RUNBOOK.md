## Exact downloadable acceptance artifacts

Use **only** the green `main` workflow for the candidate being tested, then
download the artifacts from GitHub Actions. The artifacts are unpacked
payload directories uploaded with `actions/upload-artifact`, so GitHub's
download itself is one directly extractable ZIP; there must be **no ZIP
member inside a ZIP**.

Check `includes/bootstrap.php` for Core 2.6.2 and
`modules/industries/industry-catering/addon.json` for Catering 2.1.1.
A COMPLETE-UPLOAD is Core-only; use a current Catering or Landscaping
TEST-BUNDLE/REPAIR-UPLOAD when testing that industry. The repair artifact
preserves the existing site's config and data and must not be confused
with a supported full backup or automated schema upgrade.

CI ephemeral signed UPDATE tests are **not** production signed release
assets. Do not distribute that testing artifact as a signed commercial
update.

## Read-only on-host diagnostic (optional CLI evidence)

The source tree now includes `tools/host-preflight.php`. On an **authorized
staging host with shell access**, run it from a **private** checkout of the
source/tools directory rather than placing it in the webroot:

```bash
php tools/host-preflight.php /path/to/deployed/webroot
# If the installation uses an external private config directory:
php tools/host-preflight.php /path/to/deployed/webroot /path/to/private/config
```

It reports the deployed Core version, installer presence/retirement,
expected public guard files, production vendor presence, discovered
industry manifest **versions only**, and the **CLI** PHP extensions. It
never loads `config.php`, connects to the database, accesses the network,
changes permissions or writes files. It deliberately suppresses private
paths, license keys and credential values. The diagnostic is source-only;
it is **not** embedded in webroot upload packages.

This probe cannot inspect Apache/LiteSpeed, the WAF, the PHP-FPM worker's
effective permissions, actual maintenance/license state, admin sessions
or a successful backup restore. Record the redacted JSON with the host
operator's private acceptance log. Do not upload it as a public
`diagnostics.php` endpoint or conclude that a passing static preflight
resolves the observed HTTP 403/503.

## Staging preflight (record results)

1. Confirm authorized staging site and full, independently restorable backup.
   Record host vendor/control panel, web server, PHP version/extensions,
   PHP-FPM identity, MySQL or MariaDB version, document root and URL path.
2. Capture current installed Core/module versions and canonical hostname
   before changing files; preserve `config/`, `storage/`, `upload/`,
   customer media and module-owned data.
3. Verify free disk space, staging/backup path ownership, writable settings,
   SSL and real mail hostname independently. Do not weaken trust settings.
4. Verify the exact downloaded artifact digest and `addon.json`/update
   manifest against the corresponding tested commit. Inspect extracted
   hidden guard files and confirm no embedded ZIPs, private keys or
   runtime `config.php` are present.
5. Confirm existing active customer content and IDs before migration.
   Create unique, non-sensitive test records for pages, menus, inquiries,
   branding and navigation; preserve a pre-upgrade audit record.

**NO-GO** until the blocked external staging access is diagnosed by the
authorized operator, the above host matrix has actual redacted evidence,
the production Ed25519 public trust root and signing process are approved,
the real licensing flow passes without enabling unauthorized payments,
the exact clean release artifacts and SBOM are reviewed, the published
asset bytes match their checksums, and the owner approves publication.

Owner approval and production credentials must **not** be inferred from
green GitHub Actions. Never commit secrets or copy customer data to CI.
