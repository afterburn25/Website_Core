## Destructive package-purge table isolation

Core now escapes both the configured database prefix and the module table
prefix before the irreversible `purgeData()` table discovery query.
Unescaped SQL `LIKE` underscores previously matched arbitrary characters:
purging `catering_` could also target a different `cateringx...` table,
and an underscore in the database prefix could match a separate namespace.
An explicit `ESCAPE '!'` clause has portable MySQL/MariaDB/SQLite
behavior and preserves literal underscores and percent signs.

SQLite package-manager tests and native MySQL 8.4/MariaDB 11.4 tests now
plant a module-owned table plus two *different* similarly named tables,
perform a real uninstall and purge, and verify only the intended module table
is destroyed, with other customer data intact. Count this as verified only
after exact-head CI passes. Purge remains **irreversible** and requires
operator backup and confirmation on actual customer hosts.

## Recovery symlink guard acceptance

The candidate now forbids symbolic links in backup source roots/files and
restore destination ancestors (not only the final file). Regression tests
require a changed linked parent and a same-content linked final file to be
refused **before** any database import or off-root write. Snapshot SHA-256
hashes are generated from the copied staging files. CI must pass on the
exact candidate commit before this hardening is credited; production
permission/ownership and actual shared-host restore remain open.

## Core update and rollback destination symlink hardening

A further acceptance fix refuses an UPDATE or rollback archive if any target
path below the deployed site root is a symlink, including a linked intermediate
directory, a same-content linked final file or a redirect into a sibling path
that merely shares the webroot's string prefix. All candidate destinations are
checked **before** the first site file changes, then checked again at write
time. Newly created staging files use unpredictable, exclusively created
temporary names instead of a predictable `.tmp-<PID>` name that could be
pre-planted as a symlink.

Automated regressions cover outside-root redirection, existing final links,
malicious temporary-file links, and fail-closed rollback without partial site
writes. **Only mark this code hardening verified after exact-head CI passes.**
It does not close the remaining production signed-update, PHP-FPM filesystem
ownership, shared-host rollback or operator-release approval gates.

## Verified pre-update rollback requirement

The Core update path now fails closed unless it can create **and read back**
a complete rollback ZIP of all existing files that the update would replace.
All saved members must match the original SHA-256 content before **any**
Core file is changed. Snapshot creation, member reads, ZIP finalization, and
read-back failure are pre-write aborts rather than best-effort warnings.
Unique random-suffixed backup names prevent two updates within one second
from overwriting each other's recovery points. CI exercises an obstructed
backup directory and two successive updates, including the distinct original
contents of both verified snapshots.

Mark this code hardening verified only after exact-head CI passes. The
remaining real shared-host backup/download/restore and update rollback gates
stay open until the operator proves them on a protected, disposable staging
site with the actual filesystem ownership and PHP-FPM identity.

## Literal-boolean licensing authorization contract

Both install-time and periodic Core licensing validators now recognize
only HTTP 200 responses with a literal JSON boolean `authorized` field.
Missing/typed-as-string/numeric/null verdicts remain inconclusive, and
the prior valid license record must be preserved for recovery. Explicit
`false` is a denial; explicit `true` is authorization. Test fixtures
exercise the wire contract and safe handling of malformed error messages.
Count this as **mock HTTP contract acceptance only after exact-head CI
passes**, not real licensing-service or paid purchase acceptance.

## CI artifact handling

The `artifacts` job builds `COMPLETE-UPLOAD`, `UPDATE`,
`FULL-PROJECT`, reference packages, and their SHA-256 manifest. It already
publishes direct Catering and Landscaping test/repair artifacts. This
release-readiness change adds direct, extracted `COMPLETE-UPLOAD` and
`FULL-PROJECT` **CI acceptance downloads**: GitHub Actions creates the
one download ZIP itself, so no built ZIP is placed inside another ZIP.
Hidden protection files must be preserved.

**Do not present CI Actions downloads as a signed production release.**
An Actions download is recompressed by GitHub, so its downloaded ZIP
checksum is not the checksum of the original `/tmp/dist/*.zip` builder
artifact. For an immutable release, verify the bytes of the *published*
release assets against checksums generated for exactly those bytes.
The CI-generated `UPDATE` remains contract-tested but is not published
as a ready-to-install update until the signing/trust and hosted checks pass.

## Additional release-acceptance automation (candidate, not live approval)

A proposed CI hardening change runs on **native MySQL 8.4 and MariaDB
11.4** to create, inspect, intentionally modify and restore an isolated
database plus protected configuration/upload fixtures. This adds a **real
database restore round-trip** to the existing backup-creation and
module-rollback evidence. It does not reproduce the permissions and PHP-FPM
behavior of the actual shared host; that host gate remains open.

The artifact job also generates a **temporary Ed25519 keypair inside CI**,
builds a signed Core UPDATE from the actual source and production-vendor
payload, and verifies that production-style trust accepts only the valid
signature while refusing unsigned, wrong-key, altered-manifest and
tampered-payload inputs. CI deletes the ephemeral private key and never
publishes that simulated signed UPDATE. Production `trust.public_keys`,
the real signing key, and the live signed-upgrade/recovery check remain
owner-controlled and **not yet complete**.

The release builder must fail closed if `WC_UPDATE_SIGN_KEY` is specified
but invalid or sodium signing is unavailable. Licensed-bundle build logs
must not print the embedded customer license key. All these controls must
pass on the exact release candidate before being marked verified; a PR
implementation alone is not proof.
